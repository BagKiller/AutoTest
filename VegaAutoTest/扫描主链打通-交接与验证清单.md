## 1. 这次要解决什么

需求文档第三节主流程的第 10–14 步（创建 Recipe → 设参 → 执行检测 → 等待完成 → 获取结果）此前一步都跑不了，根因是 `AgentControlService` 只注册了一个写命令 `recipe/open`，且它仅改存储层 `IsOpen` 标志，并没有驱动真实业务流程。

本次在插件里补齐了这条链的可编程入口。

### 关键勘察结论（决定了实现方案）

| 结论 | 影响 |
|---|---|
| Simulator 模式**默认已开**（`RootCondition = Vega500,Simulator,GemSim,Gen2`） | 不需要切配置 |
| `IGEMService.RunCurrentRecipeAsync(recipeId, scanNum)` 是干净入口，且会 await 到扫描结束 | 选它作为扫描主入口，不用 Job 队列 |
| 扫描路径上有**模态弹窗**（`TryResolveFsPreOpen`、失败重试框） | 扫描必须做成异步任务，HTTP 绝不能同步等 |
| 上片必须 `PrepareManualLoad` → `LoadWaferManually` **两步**，顺序不能颠倒 | 照 `ManualWaferHandlerViewModel` 复刻 |
| `PrepareManualLoad` 内部会 `MoveXAxis` | **上片前 Motion 必须已 Home**（先做 Full Initialize） |
| Recipe 创建走 `NewFileAsync`，创建即入库，不需要再 Save | `recipe/create` 不依赖 UI 线程 |
| **Vega 没有 Total Die / OK / NG 模型** | 需求文档第十五节的断言示例（`Total Die = 100, NG <= 5`）不符合实际业务，必须改写 |

最后一条要特别注意：Vega 是**缺陷检测**模型，结果语义是 `EffectiveDefectCount`、`FusedDefects`、`CounterInfos`（名值对）、`IsScanSuccessful`。后续写断言要基于这些字段，不要照搬需求文档的 die 计数示例。

## 3. 新增的 HTTP 接口

### 只读查询（GET，不受 `AllowHardwareCommands` 约束）

| 端点 | 用途 |
|---|---|
| `query/run-readiness` | **最重要**。一次返回「现在能不能跑扫描」+ 缺什么（`blockers` 数组） |
| `query/recent-wafer-runs?limit=5` | 最近 WaferRun 轻量清单（投影读取，不物化缺陷） |
| `query/wafer-run?id={waferRunId}` | 单次 WaferRun 的**可断言标量集**（状态、成功标志、缺陷数、Counter、耗时） |
| `query/scan-task?id={taskId}` | 轮询扫描任务；不带 `id` 返回全部任务概览 |

`run-readiness` 的 `blockers` 可能取值：`gem_service_unavailable`、`wafer_handler_unavailable`、`recipe_provider_unavailable`、`tool_state_unavailable`、`tool_state_not_idle:{状态}`、`gem_state_query_failed`、`job_run_state_not_idle:{状态}`、`no_wafer_on_stage`、`wafer_state_query_failed`。`blockers` 为空数组时 `canRunCurrentRecipe=true`。

### 写命令（`POST /vega-agent/cmd/{name}`，**需要 `AllowHardwareCommands=true`**）

| 命令 | body | 说明 |
|---|---|---|
| `recipe/create` | `{"name":"<名字>", "folderId":0, "open":false}` | 等价 UI 新建，立即入库。服务端校验非法字符 `\ / : * ? " < > \|` |
| `wafer/load` | `{"slot":1, "diameter":300, "portNum":0, "waferId":"<可选>"}` | 手动上片，仿真下不走 EFEM。已有片时直接返回 `alreadyLoaded=true` |
| `wafer/unload` | `{}` | 手动下片 |
| `scan/start` | `{"recipeId":<long>, "scanNum":1}` | **异步**，立即返回 `taskId`，用 `query/scan-task?id=` 轮询 |

`scan/start` 的设计要点：投到后台任务，单飞（同时只允许一个扫描）。启动前会自检 `LoadedWafer != null` 和 `JobRunState == Idle`，不满足直接返回结构化错误而不是盲目启动。任务完成后，用「扫描前后 waferRunId 集合做差集」定位本次产生的 WaferRun（比「取最新一条」稳，不依赖分页返回顺序），并把结果摘要直接塞进轮询响应，一次轮询就能拿到「跑完了 + 结果如何」。

### 4.4 分步验证（按顺序，每步确认再往下）

启动 Vega 后等约 5 秒（`DelayStartSeconds=5`）。

```powershell
$b = "http://localhost:18901/vega-agent"

# 1. 服务活着吗，开关开了吗
irm "$b/ping" | ConvertTo-Json -Depth 5

# 2. 关键一步：现在离能跑扫描差什么
irm "$b/query/run-readiness" | ConvertTo-Json -Depth 6
```

第 2 步是整个验证的核心。**刚启动时预期会看到 blockers**，大概是 `tool_state_not_idle:Boot`（还在启动）和 `no_wafer_on_stage`。先重点看 `services` 字段——如果 `gem`、`waferHandler`、`measurement` 有 `false`，说明服务定位失败，后面都白搭，这是最需要优先确认的事。

```powershell
# 3. 在 Vega 界面上手动做 Full Initialize（菜单），等 toolState 变 Idle
#    这一步我没有自动化，需要你点。之后重新看 readiness：
irm "$b/query/run-readiness" | ConvertTo-Json -Depth 6

# 4. 建一个 Recipe
$r = irm -Method Post "$b/cmd/recipe/create" -ContentType "application/json" `
     -Body '{"name":"AUTOTEST_SCAN_001","folderId":0,"open":true}'
$r | ConvertTo-Json -Depth 5
$recipeId = $r.recipe.ID

# 5. 上片（最可能失败的一步，见下面风险清单）
irm -Method Post "$b/cmd/wafer/load" -ContentType "application/json" `
    -Body '{"slot":1,"diameter":300,"portNum":0}' | ConvertTo-Json -Depth 5

# 6. 确认 canRunCurrentRecipe 变 true
(irm "$b/query/run-readiness").canRunCurrentRecipe

# 7. 启动扫描（立即返回）
$t = irm -Method Post "$b/cmd/scan/start" -ContentType "application/json" `
     -Body (@{recipeId=$recipeId; scanNum=1} | ConvertTo-Json)
$t | ConvertTo-Json -Depth 5

# 8. 轮询直到 state 不是 running
while ((irm "$b/query/scan-task?id=$($t.taskId)").state -eq "running") {
    Start-Sleep -Seconds 5
    "still running..."
}
irm "$b/query/scan-task?id=$($t.taskId)" | ConvertTo-Json -Depth 8
```

第 8 步的最终输出里 `waferRuns[0]` 就是这次扫描的可断言结果摘要。

## 5. 风险清单（按可能性排序）

1. **`wafer/load` 失败（最可能）**。`PrepareManualLoad` 会驱动 Motion 移轴，底层 `MotorCheckForMove` 强制要求「已 Home + 已 Enable + 速度>0」，而仿真下 Motion 初始 `_allHomedFlag=false`。如果 Full Initialize 不包含 Stage Home，需要去诊断页手动 Home。命令返回里我加了 `hint` 提示这一点。

2. **`ManualHandler` 的 `ML` feature 问题**。当前 Vega500 的 `Features` 是 `EFEM,LPM,DIC,EdgeChuck`，**不含 `ML`**，所以 UI 上看不到 Manual Handler 页。我的假设是「feature 只控制 UI 树可见性，服务 API 仍可调」——**这个假设未验证**。如果 `wafer/load` 报意外错误，先怀疑这里。备选方案是走 EFEM 路径 `LoadWaferFromCarrierToStageAsync`（需要 carrier + slot mapping，复杂得多）。

3. **扫描任务卡在 `running`**。说明命中了模态弹窗（`TryResolveFsPreOpen` 或失败重试框）。HTTP 不会挂死（这是异步设计的目的），但任务不会自己结束。去 Vega 界面看有没有弹窗并手动关掉。长期方案是让 L2 UIA 的 `DialogHandler` 守着自动关——这正是混合通道该干的事。

4. **`ToolStateHelper(ToolState.Busy)` 抛异常**。`ToolState` 处于 `Boot`/`Locked` 时构造可能失败，会被 HTTP 管道 catch 成 500。先确认 `toolState=Idle` 再发写命令。

5. **BSS 相关可能空图**。`Resources\Data\BSSCameraImage.tif` 不在仓库里，`Mercury3CameraSim` 构造时读它。不确定会不会影响扫描主链。

6. **waferRunId 差集法的边界**。我用扫描前后各取 50 条分页快照做差集。如果 `scanNum` 很大或期间有别的运行写库，可能多识别。单飞锁能挡住本服务内的并发，挡不住 UI 上人工同时跑。
