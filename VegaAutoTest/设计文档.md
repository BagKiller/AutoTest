# VegaAutoTest 自动化回归测试系统设计文档

> 本文档是 VegaAutoTest 系统的**实现依据**。
> 需求来源：`需求文档.md`（目标、业务流程、能力要求）。
> 背景知识：`自动检测工作流技术文档.md`（CUA 原理解读，**不作为实现依据**——其中"GPT-6 Astra"查无实据，真实对标系统为 OpenAI Operator / Claude computer use / UI-TARS / Microsoft UFO / Agent-S；该文档仅用于理解纯视觉 Agent 路线的原理与局限）。

---

## 1. 核心设计原则

| # | 原则 | 说明 |
| --- | --- | --- |
| P1 | **通道由提交类型决定** | Diff 分析先判定提交类型，再选执行通道；不存在"一条通道包打天下" |
| P2 | **确定性优先，AI 做复杂判断** | 观察（UIA 树 diff）、验证（断言/基线对比）、状态判定全部确定性；LLM 只负责 Diff 理解、用例规划、异常归因 |
| P3 | **内部状态与 UI 表现互为印证** | 界面显示必须与内部状态交叉验证（防"界面显示成功实际没生效"类 Bug） |
| P4 | **证据链完整可追溯** | 每次运行留下从 Commit 到报告的全量证据，FAIL 必须人 review 确认 |
| P5 | **经验沉淀为一等资产** | 每次成功运行自动沉淀为可回放 DSL 用例 + 基线快照，用例库越用越准 |

### 1.1 对标系统的借鉴与取舍

借鉴自真实生产级系统（非虚构的"GPT-6 Astra"）：

| 前沿机制 | 来源 | 本系统的对等实现 |
| --- | --- | --- |
| 结构化接口优先，GUI 是最后手段 | Anthropic/Claude computer use 官方建议 | 三通道分层，L3 视觉仅兜底 |
| Manager/Operator 分层 | UI-TARS、Microsoft UFO | Orchestrator（LLM 规划）+ Harness（确定性执行） |
| 经验记忆（experience memory） | UI-TARS、Agent-S | DSL 用例库 + golden master 基线库 |
| 沙箱与回滚 | OpenAI Operator 云端 VM | Simulator 模式 + 独立 worktree + 干净环境 |
| 敏感度分级门禁 | Operator takeover/watch mode | 只读放行 / 写操作配置门 / FAIL 转人工 |
| 失败反思循环 | UFO、Agent-S reflection | 证据收集 → LLM 归因 → 分级重试（封顶转人工） |
| GUI Grounding | CUA 类系统核心壁垒 | **基本不需要**：WPF 原生暴露完整 UIA 树，`AutomationId` 即精确 grounding；仅 L3 兜底通道采用 Set-of-Mark 类技术 |

明确不采纳：以"截图 → 视觉理解 → 输出坐标"为主循环的纯视觉 CUA 路线。理由：Vega 是自有代码库，WPF 一等公民支持 UIA，视觉定位是给"无接口软件"准备的最后手段；且 Anthropic 官方文档明确建议"能走常规 API/工具就不要走屏幕操作"。

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────┐
│              Orchestrator（Claude Code / CLI 驱动）         │
│  ① Diff 分析 → ② 提交分类 → ③ 用例规划 → ④ 编排执行          │
│                    → ⑤ 失败归因 → ⑥ 报告生成                │
└───────────────────────────┬──────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────┐
│              Test Harness（独立 .NET 8 控制台）             │
│   状态机 · DSL 解释器 · 三通道适配 · 确定性验证器             │
│   基线管理 · 证据采集 · 超时/重试 · Recovery                 │
└─────┬─────────────────────┬─────────────────────┬────────┘
      │                     │                     │
┌─────▼─────┐        ┌──────▼──────┐       ┌──────▼──────┐
│ L1 进程内  │        │ L2 UIA      │       │ L3 视觉     │
│ API 18901 │        │ FlaUI + 截图 │       │ 截图 + VLM  │
│ 数据/流程  │        │ 真实控件行为  │       │ 盲区兜底     │
└─────┬─────┘        └──────┬──────┘       └──────┬──────┘
      └─────────────────────┼─────────────────────┘
                            ▼
                   Vega（Simulator 模式为主）
```

- **Orchestrator** 复用 Claude Code 既有能力（代码阅读、Diff 分析、`log-analyzer`/`troubleshoot` 式归因），不自研 Agent 框架。
- **Harness** 放在 `VegaAutoTest/harness/`，独立解决方案，**零 ProjectReference 引用 Vega 项目**——只通过 HTTP（L1）、FlaUI（L2）、文件系统/进程（构建与启动）与被测系统交互，不触碰 Constitution 的分层与装配约束。
- 技术栈：C# / .NET 8（与仓库一致）、FlaUI.UIA3、xUnit 风格的用例组织但自研 DSL 解释器。

## 3. 三通道设计

### 3.1 通道选择决策表（核心）

| 提交类型（Diff 判定） | 主通道 | 辅助通道 | 验证方式 |
| --- | --- | --- | --- |
| 业务逻辑类（`Vega.BL.*`、`Vega.LD.*`、`Vega.PD.*`） | L1 API | L2 验证入口/出口 UI 表现 | 确定性断言（结果数值、状态迁移） |
| 纯 UI 类（XAML、样式、交互逻辑、ViewModel） | **L2 UIA + 截图** | L1 做辅助 oracle（界面显示与内部状态一致） | UIA 树断言 + golden master 对比 |
| 视觉样式类（颜色、布局、主题） | 截图基线对比 | VLM 辅助判断差异是否刻意 | 基线 diff + 人 review |
| 混合类 | L1 主流程 + L2 逐步观察 | — | 两者叠加 |

### 3.2 L1 进程内 API 通道

承载 `Vega.BL.AgentControlService`（本地插件，HTTP，端口 18901）。现状与扩展见第 6 节。

适用：Recipe 管理、参数设置、扫描启停、状态查询、结果获取、日志尾读——完整检测流程的主干。

### 3.3 L2 UIA 通道（"点击后时刻观察反应"的实现）

WPF 对 UI Automation 是一等公民支持：控件树、文本、位置、Enabled/Visible 状态、`AutomationId` 全部可编程读取。**观察是确定性的树操作，不靠人眼看截图。**

核心循环：

```
① FlaUI 读 UIA 树（快照 A）
② 执行动作（InvokePattern / SelectionItemPattern / ValuePattern...，
   与真人点击走同一套 Command 绑定）
③ 点击后 100ms ~ 数秒内再次读树（快照 B），做结构 diff：
   - 新 Window 出现？        → 弹窗打开了
   - 控件 Enabled 变化？     → 按钮置灰了
   - 文本 / 可见性变化？      → 状态更新了
   - DataGrid 行数 / 内容变化？→ 数据刷新了
④ 前后各存一张截图 + diff 结果写 timeline（证据链）
⑤ 断言：用例声明的"预期反应"是否发生
```

增强能力：

- **UIA 事件订阅**（`StructureChangedEvent`、`AutomationPropertyChangedEvent`）：点完不等轮询，事件驱动捕捉界面变化——真正的"时刻观察"。
- **控件定位策略**（修正需求文档第六节优先级）：`AutomationId` > `Name` + ControlType + 树路径 > 截图 + VLM（仅盲区）。OCR 降级为不实现——WPF 场景下 UIA 覆盖率远高于 OCR，自绘控件盲区直接走 VLM。
- **前置工程约定**：为关键可测控件补 `AutomationId`（`AutomationProperties.AutomationId`），纳入 code review 检查项。这是 L2 通道稳定性的地基，成本极低。

L2 用例 DSL 示例：

```yaml
steps:
  - action: uia.click
    target: { AutomationId: btnStartScan }
  - action: uia.expect              # 点击后的预期反应
    expect:
      window_appears: { Title: 检测确认, buttons: [确定, 取消] }
  - action: uia.click
    target: { Name: 确定 }
  - action: uia.expect
    expect:
      window_closed: 检测确认
      status_text_contains: 扫描中
verify:
  - screenshot_diff: baseline/start_scan.png   # 布局无意外变化
  - api.state == Running                        # 辅助 oracle：内部确实在跑
```

### 3.4 L3 视觉兜底通道

仅用于：自绘控件、UIA 树读不到的第三方弹窗、异常现场理解。

- 技术路线：截图 + Set-of-Mark 类 grounding（VLM 返回目标 bbox）+ 确定性执行点击。
- 输出始终带截图证据；VLM 判断不直接作为 PASS 依据，只作为"定位到哪、看到了什么"的归因材料。
- 不做 OCR 独立层级。

### 3.5 "预期效果从哪来"

没有任何生产级系统能纯靠 Diff 推断 UI 改动的预期效果。本系统的两个锚点：

1. **功能性行为**（点了弹窗、按钮置灰、文本变化）→ 写进用例的 `uia.expect` 断言；
2. **视觉类改动**（布局、颜色、间距）→ **golden master 基线**：改动合入前人工跑一次，Harness 录制 UIA 树快照 + 截图作为基线；此后每次回归自动对比，差异超容差即标红并附对比图，**由人 review 报告确认**，VLM 只做"该差异是否刻意"的辅助判断。

## 4. Harness 设计

### 4.1 职责边界

Harness = 操作 + 观察 + 断言 + 证据的测试脚手架。它不关心动作经由哪条通道执行——通道是它的可插拔工具。**它不等于 API 监控**。

### 4.2 状态机（落在 Harness，不侵入 Vega 主程序）

正常路径与异常状态沿用需求文档第八节定义。每个状态声明：进入条件、执行动作、成功条件、失败条件、超时时间、重试策略、Recovery 策略。

异常统一处理路径：

```
任一状态异常
→ 存证（截图 + UIA 树 dump + 日志尾读 + 内部状态快照）
→ LLM 归因
→ 决策：retry（同通道）/ 换通道重试 / skip / abort 转人工
→ 重试有分级封顶，封顶后 FAIL 并转人工
```

典型 Recovery 场景（软件崩溃重启、设备离线重连、未知弹窗分类处理、扫描超时收集归因）沿用需求文档第十三节，实现于 Harness 的 Recovery 策略表。

### 4.3 用例库与 DSL

目录结构沿用需求文档第十二节（recipe / camera / motion / detection / result）。统一 YAML DSL，关键字段：

```yaml
test:
  name: wafer_scan_regression
  channel: api            # api | uia | vision | mixed，决定主执行通道
  preconditions:
    simulator: true
    recipe: AI_REGRESSION_001
  steps: []               # 按 channel 语义解释，见 3.3 / 4.4 示例
  verify: []              # 确定性断言：表达式 / screenshot_diff / api.state
  on_fail: evidence.collect + ai.analyze
```

`verify` 只用确定性规则（数值断言、状态断言、基线 diff），禁止"AI 看图判断 PASS"。

### 4.4 一条完整混合用例示例

```yaml
test:
  name: edge_detection_regression
  channel: mixed
  preconditions:
    simulator: true
    recipe: AI_REGRESSION_001
  steps:
    - action: api.recipe.open        # L1：数据层加载
      args: { name: AI_REGRESSION_001 }
    - action: api.scan.setParams
      args: { exposure: 100 }
    - action: uia.navigate           # L2：UI 路径回归（模拟人工入口）
      path: [Inspection, ScanSetup]
    - action: uia.expect
      expect: { text_contains: { target: exposureBox, value: "100" } }  # UI 与内部一致
    - action: uia.click
      target: { AutomationId: btnStartScan }
    - action: wait
      until: api.scan.status == Completed
      timeout: 600
    - action: api.result.fetch
  verify:
    - expr: result.totalDie == 100
    - expr: result.ng <= 5
    - expr: result.scanTime < 600
    - screenshot_diff: baseline/scan_result.png
```

### 4.5 基线管理（golden master）

- 位置：`VegaAutoTest/baselines/<用例名>/<Vega 版本或 commit>/`。
- 内容：全屏/窗口截图 + UIA 树序列化快照。
- 对比：截图做像素 diff（容差可配）+ 控件树结构 diff（位置/尺寸容差）；差异产出并排对比图。
- 更新流程：基线变更必须伴随人 review（防"把 Bug 录成基线"）。

### 4.6 证据链与报告

每次运行一个目录（沿用需求文档第十四、十五节）：

```
runs/2026-09-10_35b844b3_edge_detection_regression/
├── meta.json          # commit、build、用例、参数、环境、通道决策及理由
├── build.log
├── timeline.jsonl     # 每步：时间戳/通道/动作/观测(树diff或状态)/结果
├── evidence/          # 截图、UIA 树 dump、日志切片、基线对比图
├── result.json        # Expected vs Actual
└── report.md          # PASS/FAIL + AI 归因（FAIL 必须人 review）
```

## 5. Orchestrator（AI 职责边界）

| 环节 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| Diff 分析 | commit message、git diff、涉及项目 | 提交类型 + 影响模块 | 映射到 Living SPEC `modules/index.md` 提高模块判定准确率 |
| 用例规划 | 提交类型、影响模块、用例库索引 | 执行的用例清单 + 通道决策 | 优先复用既有用例；无匹配用例时降级为"冒烟集 + 转人工补用例" |
| 异常归因 | evidence/ 目录 | 归因报告 + 重试决策 | 复用 `log-analyzer` / `troubleshoot` 的方法（代码为主证、日志为路标） |
| 报告生成 | result.json + timeline | report.md | FAIL 结果必须人 review 后才算终态 |

LLM 不输出坐标、不直接驱动 GUI、不判定 PASS——三通道与状态机是它的唯一手臂。

## 6. AgentControlService 现状与扩展

### 6.1 现状（本地已存在，gitignore 中）

- `Vega.BL.AgentControlService` / `Vega.BL.IAgentControlService`（**2026-09-21 已转正入库**，在 Vega.sln / Vega.csproj）。
- HTTP 通道（HttpListener），端口 18901，配置 `Vega/Resources/Configs/AgentControlService.json`（`DelayStartSeconds=5`，`AllowHardwareCommands=false`）。
- 已有端点：`/ping`、`/query/tool-state`、`/query/recipe-list`、`/query/opened-recipe`、`/query/recipe?id=`、`/cmd/recipe/open`（后者需 `AllowHardwareCommands=true`）。
- 命令注册表模式（`_commandHandlers`），新增命令不改 HTTP 管道。
- 部署约束：插件必须编译进主程序（`run-vega-with-plugin.ps1` 临时注入 ProjectReference → MSBuild x64 → 还原）；需 URLACL 预注册；MongoDB 前置。

### 6.2 扩展命令（P1 范围）

全部复用 BL 层既有接口（`IWaferRun`、`IRecipeStorageProvider` 等），不新增平行实现：

| 命令 | 类型 | 作用 | 对应 GUI 步骤 |
| --- | --- | --- | --- |
| `recipe/create` / `recipe/save` | cmd | 数据层建/存配方 | 创建/保存 Recipe |
| `scan/set-params` | cmd | 写扫描参数 | 配置检测参数 |
| `scan/start` | cmd | 触发 WaferRun | 开始检测 |
| `scan/status` | query | ScanStatus 轮询 | 等待扫描完成 |
| `scan/result` | query | Total Die / OK / NG / 耗时 | 查看结果 |
| `app/logs-tail` | query | 尾读 Serilog 日志 | 异常证据收集 |

安全模型沿用现有三级门禁：query 默认放行；写命令需 `AllowHardwareCommands=true`（建议仅 Simulator 环境开启）；真机配置默认关闭。

### 6.3 转正决策（P1 前置）

AgentControlService 是 L1 通道地基，建议转正入库：移除 `.gitignore` 对应条目、加入 sln、按 Constitution 补组件装配检查（接口在 `I*` 项目、RunOrder 落服务段、评估 Sim 配对约束适用性）。转正前继续用 `deploy-plugin.ps1` 本地部署。

## 7. 分阶段实施路线

| 阶段 | 内容 | 完成标志 |
| --- | --- | --- |
| **P0 闭环打通** | Harness 骨架（状态机 + timeline + 证据目录）；构建脚本（MSBuild x64 + 插件注入）；启动 → ping 轮询 → tool-state 查询 | 一条命令完成 build→launch→探活→落一份 timeline |
| **P1 API 主通道** | AgentControlService 转正 + 扩 6.2 命令；Sim 模式跑通"建/开 Recipe → 设参 → 扫描 → 取结果" | 首条 L1 用例端到端 PASS |
| **P2 用例化** | DSL 解释器 + 确定性验证器 + 基线管理 + report.md 生成；沉淀首批用例（recipe/detection 各 2~3 条） | 用例库可被 Orchestrator 检索与规划 |
| **P3 UIA 通道** | FlaUI 接入；关键控件补 AutomationId；`uia.expect` 断言 + 树 diff + 事件订阅；首批纯 UI 类用例 | 纯 UI 提交可自动回归 |
| **P4 视觉兜底 + AI 归因** | Set-of-Mark grounding；失败自动归因接入；golden master 全流程（含人 review 更新基线） | 盲区弹窗可处理；FAIL 报告带归因 |
| **P5 CI 集成** | Azure DevOps pipeline：PR 触发 → P0~P2 无人值守 → 报告回帖 | Commit 到报告全自动闭环 |

P0–P2 完成后主链路（Commit → 报告）在 Simulator 模式端到端可用；P3 补齐"点击后观察 UI 反应"能力；P4/P5 为增强与固化。
