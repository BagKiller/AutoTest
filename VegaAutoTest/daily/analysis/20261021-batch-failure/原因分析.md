## 3. Runner 把普通断言失败连续误归因为两种工具错误

原始链条为：

```text
Assert.Equal(1, 0)
  → VerdictResolver: ERROR / HARNESS_EXCEPTION
  → ResultContractCheck: ERROR / CONTRACT_VIOLATION
  → 日报：验证工具异常
```

### 第一层：命名空间决定是否算断言失败

`runner/Vega.AutoTest.Runner/VerdictResolver.cs:135-160` 的 ClassifyFailures：

- 消息出现“主窗口/MainWindow”就归环境超时；
- 出现“空闲/idle”就归设备未空闲；
- 出现 `.L2.` 才认作用例自身断言失败；
- 其余统统算 harnessFailures。

失败的真实类型是 `Xunit.Sdk.EqualException`，命名空间是 `.CommitProbe.`，没有 `.L2.`，因此被错误分类。且 HARNESS_EXCEPTION 分支在结构化 `assertions.result=FAIL` 检查之前返回，已记录的失败断言也没能纠正归因。

这意味着同一种 Assert 失败，仅因测试放在 logic 工程还是 L2 工程，最终结果可能不同。它是测试基础设施缺陷，不是产品多出了一个独立故障。

### 第二层：纯逻辑测试被错误要求存在 UIA 通道

`runner/Vega.AutoTest.Runner/ResultContractCheck.cs:37-44`：

```text
任意测试失败 && verdict=FAIL/ERROR && summary.passed>0 && l2Uia.available=false
  → CONTRACT_VIOLATION
```

这里的 `hasUiaFailures` 实际并未判断失败来自 UIA，只判断“存在任意失败”。纯 logic 测试有一条失败、其他断言通过，是完全合法的组合，却被契约检查否决。

所以报告中的 HARNESS_EXCEPTION 与 CONTRACT_VIOLATION 是同一条断言的错误包装，不能作为两个独立环境问题来修。

## 4. #3661 明明通过，却被历史工作项号卡住

提交 `0d154c77` 的正文为：

```text
关联工作项：#3661（前批：#3633 / PR 4930）
相关工作项: #3661
```

`daily.py:119-124` 的 work_items 对全文匹配所有工作项号，返回 `[3633,3661]`。它排除了 PR 编号，却没有区分**本次修复工作项**和**历史背景引用**。

随后 `daily.py:480-521` 的 evaluate 要求每个工作项簇都有登记用例；#3633 没登记，于是即使 #3661 的 180 条断言通过，提交仍记 NEEDS_CASE。

同类问题还出现在 `3cfb97a1`：正文把 #3609 作为早期回归来源，当前工单是 #3649；两者被平级纳入必验清单。此处不能简单断言 #3609 完全不需回归，但它不应在没有明确范围定义时自动变成关闭当前提交的强制门禁。

正确方向是分别记录 `primaryWorkItems`、`relatedWorkItems`，优先结构化关联或明确的本次工单声明，并支持人工维护的可审查映射。不能靠删除所有历史数字，也不能把同一组测试随意复制挂到多个工单来掩盖缺覆盖。

## 5. 一组大探针混合多个需求，失败归属失真

`daily-supplement` 同时包含：

- #3652 的 Binning 原始产品行为测试；
- 采集空字节交付、取消、超时和跨 run 会话栅栏；
- Vega100 EdgeScan 资源检查；
- Vega100 LPD 过滤与保存检查。

registry 将整个大用例关联 #3652，且标记 partial-acceptance。原始结果中 Binning 断言都通过，失败来自采集取消，但 #3652 提交被标成 ERROR。

同一大用例又作为路径探针关联其他提交，因此一条采集断言会在多个提交的证据列重复出现。重复行不是多个独立故障。

即使修掉这条失败，#3652 仍可能只到 PARTIAL，因为登记本身就声明它不是完整验收。这是验收设计决定的，不是重跑次数不足。

## 6. 当前每日系统能执行登记套件，尚不能自动完成新工作项验收

“收集所有提交”已经实现；“每个新工作项都产生完整可执行验收”没有实现。

- nightly plan 只从 registry 已有映射取用例。
- 最新 daily/AGENTS.md:9 明确要求不临场修改用例/断言，缺登记只报告“缺用例”。
- 因而每次出现新工作项，如果没有提前登记用例，就会继续进入 NEEDS_CASE。
- 未关闭提交进入 pendingCommits，次日重新编入；如果没有补覆盖的阶段，同一批缺口会每天重现并不断累积。
- #3663 的提交里已经带有 `SummaryExportContentTests.cs`、`ExpandStarColumnsTests.cs`，但 nightly 不自动纳入这些产品测试；“产品仓库有测试”和“批次计划登记并运行了测试”是两回事。
- 路径分类是固定关键字规则；#3667 的 XilinxCardDeviceProxy/QT1426CardDevice 改动没有命中当前规则，manifest.groups=[]。因此路径探针和真机清单也不是完整语义分析结果。

所以把计划收集、顺序执行、输出文件都称为“全自动验收完成”，超出了现有实现能力。

## 7. 单项与批次比较口径不一致

| 比较维度 | 单项常见口径 | 本次批次口径 |
| --- | --- | --- |
| 产品版本 | 某次固定旧目标，例如 985a08aa | master 最新合并结果 95460cda |
| 覆盖范围 | 一个工作项的一组用例 | 工作项用例、共享路径探针、每日底线 |
| 判断对象 | 工作项用例 PASS | 整个提交的全部必验工单均闭环 |
| 背景引用 | 人读正文能识别“前批” | 正则把全文数字视作同级工单 |
| GUI | 单项报告可能同时保留人工/GUI缺口 | 本次没有任何登记的 UI slot |

必须对齐产品 DLL 指纹、用例版本、配置、覆盖范围、判断对象后才能说“单跑通过、合跑失败”。当前数据不支持这种概括。

批次代码按用例顺序调用 run_case；Runner 按 layer 顺序调用 TestRunner.RunLayer；每层启动新的 dotnet test 子进程。没有发现本次由于批次并行或跨层静态状态污染而失败的证据。独立运行复现相同取消断言，进一步缩小了原因范围。

| 优先级 | 改动 | 应验证的效果 |

| P0 | 修 Runner 断言异常识别及契约检查；用结构化断言/异常信息归因，UIA 可用性只和实际 UI 层关联 | 纯 logic 一过一败合法产生 FAIL/ASSERTION_FAILED；真正宿主异常仍 ERROR；不改历史原始结果 |
