# VegaAutoTest 外挂化集成技术方案

> 目标：把 VegaAutoTest 的确定性验证能力，以"外挂"形式接入同工程下的 `VegaAutomation\code_indicator`
> 的 LLM 编排层，形成「读工作项 → 定位 → 修复 → 验证 → 总结回帖」闭环，
> 且全程不侵入主项目 `Vega_SW`。
>
> 文档版本：v1.0 ｜ 2026-09-16

---

## 0. TL;DR

| 项 | 结论 |
| --- | --- |
| 外挂定位 | **成立**。VegaAutoTest 本就零 `Vega.*` ProjectReference，隔离性已达标，无需重新设计 |
| 合并方式 | **不要**把测试重写进 Python。用**进程边界 + `result.json` 契约** |
| 核心纪律 | **LLM 只在编排层；判定层必须无 LLM** |
| 当前最大缺口 | 没有机器可读的判定产物（`result.json`），两边接不上 |
| 必须先修 | `code_indicator` 运行时工具 6/9 指向不存在的端点；PAT 明文；非 git 仓库 |

## 1. 架构

### 1.1 三层结构

```
┌──────────────────────────────────────────────────────────┐
│ L0 编排层  code_indicator/vega-agent    （Python · 有 LLM）│
│   读工作项 → 分类 → 代码检索 → 决定验证策略 → 总结 → 回帖    │
└───────────────────────┬──────────────────────────────────┘
                        │ 进程边界（子进程 + 退出码）
                        │ 数据契约（result.json）
                        ▼
┌──────────────────────────────────────────────────────────┐
│ L1 执行层  Vega.AutoTest.Runner          （C# · 无 LLM）   │
│   case registry → 可选构建 → dotnet test → 汇总 result.json│
└───────────────────────┬──────────────────────────────────┘
                        │ UIA(FlaUI) / HTTP 18901 / 文件系统
                        ▼
┌──────────────────────────────────────────────────────────┐
│ L2 被测      Vega.exe                    （零侵入）        │
└──────────────────────────────────────────────────────────┘
```

### 1.2 为什么判定层不能有 LLM

验证的全部价值在**确定性**。`WorkItem3478L2` 的意义不是"它能点界面"，
而是它每次都是同样的断言、同样的证据格式——所以 PASS 才能当证据。

一旦让模型临场决定"这次怎么验"，同时失去三样东西：

1. **PASS 不可信**：模型可能绕开难点后自我宽恕
2. **跨次不可比**：今天和明天验的不是一回事，无法建回归基线
3. **失败不可归因**：分不清是代码坏了，还是模型这次走了别的路

因此职责切分为：**模型决定「要不要验、验哪个」，程序决定「怎么验、判什么」**。

### 1.3 职责边界表

| 能力 | 归属 | 理由 |
| --- | --- | --- |
| 拉取/解析工作项 | L0 | 已实现（`tools/azure_devops.py`） |
| 缺陷分类、代码检索、根因推理 | L0 | 需要语义理解 |
| 选择用例、决定是否 rebuild | L0 | 决策，允许不确定 |
| 启动 Vega、UIA 交互、断言 | L1 | 必须可重复 |
| PASS/FAIL/BLOCKED 判定 | **L1** | 判定规则固化进代码，不进提示词 |
| 生成报告、回帖 ADO | L0 | 表达层 |
| 修改主项目代码 | L0（受策略层约束） | 见 §6 |

### 2.2 verdict 四态（**关键设计**）

必须把「代码坏了」和「环境不行」分开，否则环境问题会污染回归基线，
并让 L0 的模型误判成"存在 Bug"。

| verdict | 含义 | 退出码 | L0 该做什么 |
| --- | --- | --- | --- |
| `PASS` | 断言全过 + 至少命中 1 条 + 证据落盘 | 0 | 写"已验证"结论 |
| `FAIL` | 断言失败，被测行为与预期不符 | 1 | 写"未通过"，附断言 diff |
| `BLOCKED` | 环境/前置不满足，**无法判定** | 2 | 写"无法验证"+原因，**不得**写成 Bug |
| `ERROR` | Runner 自身异常 | 3 | 报工具故障，人工介入 |

### 2.3 verdictCode 原因码

```
OK
OK_STALE_BUILD            → PASS，但构建失败沿用了旧 exe，结论降级
ASSERTION_FAILED
NO_CASE_REGISTERED        → BLOCKED，该工作项没有登记用例
NO_TEST_MATCHED           → BLOCKED，过滤器零匹配（用例未写/被条件编译剔除）
VEGA_EXE_NOT_FOUND        → BLOCKED
BUILD_FAILED_NO_FALLBACK  → ERROR，重编失败且无可用旧二进制
MAIN_WINDOW_TIMEOUT       → BLOCKED
DEVICE_NEVER_IDLE         → BLOCKED（典型：MongoDB 缺失导致卡 busy）
L1_UNAVAILABLE_REQUIRED   → BLOCKED
ZERO_ASSERTIONS_MATCHED   → BLOCKED，用例跑完但一条都没命中 = 没真正进到目标界面
HARNESS_EXCEPTION         → ERROR
CONTRACT_VIOLATION        → ERROR，result.json 契约自检违例（仪表坏了，判定不可信）
TIMEOUT                   → BLOCKED
```

> `CONTRACT_VIOLATION` 由 P3.5 自检产生，语义是「这份 result.json 自己不可信」。
> 关键约束：**违例也必须落盘**——原判定保留在 `verdictReason` 里。
> 不落盘会把"仪表坏了"退化成"工具没反应"，L0 只能看到退出码，拿不到结构化原因
> （与 §9 决策 2「宿主崩溃也要写出 result.json」同一条理由）。

> `ZERO_ASSERTIONS_MATCHED` 单列很重要：测试"绿"但一条断言没命中，
> 是最危险的假阳性。必须当 BLOCKED 而不是 PASS。

**`HARNESS_EXCEPTION` 的归因边界**（2026-09-21 实测补充）：该码的语义是
「Runner/harness 自身坏了」，**不含用例自己的硬断言失败**。归因必须先看 trx
堆栈——含 L2 用例程序集帧（`.L2.`）即为用例断言失败，归 `ASSERTION_FAILED`。

实测踩坑：#3547 的 5 条断言失败最初被判成 `ERROR/HARNESS_EXCEPTION`
（runId `20260921T053127Z`、`20260921T053324Z`），把"被测程序不符合预期"
误报成"验证工具故障"——这是最坏的一类误判，会让 L0 去修工具而不是看代码。

### 2.4 `target.builtFromCurrentSource` 的真值表（**2026-09-21 收紧**）

这个字段是「结论对谁有效」的唯一开关，消费侧（`autotest.py` 摘要、
`wi-verify` 转述表、`SYSTEM_PROMPT` 验证纪律第 3 条）全部以
`builtFromCurrentSource == false` 作为降级表述的触发条件。因此它**只能**
表达一件事：本次跑的二进制是不是由当前源码编出来的。

| 情形 | `rebuilt` | `builtFromCurrentSource` | 结论效力 |
| --- | --- | --- | --- |
| `--rebuild` 且构建成功 | true | **true** | 对当前源码有效 |
| `--rebuild` 但构建失败、沿用旧 exe | true | **false** | 仅对旧二进制有效（+ `OK_STALE_BUILD`） |
| 未 `--rebuild`（默认） | false | **false** | 仅对该 exe 有效，必须报出 `vegaExeBuiltAt` |

即：`builtFromCurrentSource = rebuilt && buildSucceeded`。

> **反例（实现曾偏离）**：把「未重编但 exe 存在」也算 true。
> 2026-09-21 的三份产物（wi3547/wi3549/wi3478）全是
> `rebuilt=false, builtFromCurrentSource=true`——字段恒真，
> 于是 §4.3 提示词纪律第 3 条（旧二进制须标注降级）永不触发。
> exe 存在只说明「有东西可测」，与「它等于当前源码」无关；
> 尤其 `gitDirty=true` 时，工作区还有没编进 exe 的改动。
> 判定"能不能说对当前源码有效"只有一个证据：**这次重编成功了**。

### 2.5 `channels` 三字段各答一问（**2026-09-21 拆分**）

`channels` 是给 L0 看「哪条观察通道是通的」，每个字段只回答自己那一问，
不得复用：

| 字段 | 回答的问题 | 判据 |
| --- | --- | --- |
| `l1Api.available` | 18901 通道是否被断言实际消费 | 本次有 `oracle-crosscheck` 或 `l1-query` 且非全 SKIP |
| `l2Uia.available` | 本次是否执行了 uia 层 | 请求层含 `uia` |
| `assertions.available` | 结构化断言通道是否产出 | 用例 Passed 但 `assert-*.json` 缺失 → false |

> **反例（实现曾偏离）**：用 `l1Api.available` 承载「断言通道是否产出」。
> 结果 wi3478（runId `20260921T055435Z`）4 条 oracle 全 SKIP
> （用例内 L1 未就绪），`l1Api.available` 仍是 `true`——L0 读到会误以为
> 交叉验证可用，把弱验证当强验证转述。
>
> 注意 Runner 侧探活与用例侧就绪是两个时刻：Runner 探的可能是上一个
> Vega 实例，而 UIA 用例自己拉起的新实例还在 `DelayStartSeconds` 里
> （当前 60s，见《工作进展与计划》B.6）。`l1Api.available` 应以
> **断言实际是否消费到 oracle** 为准，而不是端口通不通。

### 3.2 Step 1 — harness 产出结构化断言

**问题**：现在 `CrossCheckWithRecipe` 只往 `EvidenceLog` 打散文
（`_wi3478_l2.txt`），Runner 无法可靠解析。

**做法**：不要去正则解析文本，让 harness 直接记结构化记录。

> **实施修正（P1 落地时）**：下面示例写死单文件 `assertions.json`，实际实现改为
> `Flush()` 无参 + 静态 Interlocked 序号文件名 `assert-{n:3d}.json`（落 `RunContext.Dir`），
> Runner 按 glob 聚合——同一测试进程里多个 xUnit 用例各自 Flush 时不会互相覆盖。
> 新写用例请照实现走，勿照抄示例的 `Flush(dir)` 签名。

新增 `harness/AssertionRecorder.cs`：

```csharp
// Copyright (c) Shanghai Vega Technology Co., Ltd. All rights reserved.

using System.Text.Json;

namespace Vega.AutoTest.Harness;

/// <summary>
/// 结构化断言记录器：与 EvidenceLog 并行——EvidenceLog 给人看，本类给 Runner 解析。
/// 落盘到 RunContext.Dir/assertions.json。
/// </summary>
public sealed class AssertionRecorder
{
    private readonly List<AssertionRecord> _records = new();

    public void Record(string id, string kind, string description,
                       string expected, string actual,
                       double? delta, double? tolerance, string result)
        => _records.Add(new AssertionRecord(id, kind, description,
                                            expected, actual, delta, tolerance, result));

    public void Pass(string id, string kind, string desc, string expected, string actual,
                     double? delta = null, double? tol = null)
        => Record(id, kind, desc, expected, actual, delta, tol, "PASS");

    public void Fail(string id, string kind, string desc, string expected, string actual,
                     double? delta = null, double? tol = null)
        => Record(id, kind, desc, expected, actual, delta, tol, "FAIL");

    public void Skip(string id, string kind, string desc, string reason)
        => Record(id, kind, desc, reason, "(skipped)", null, null, "SKIP");

    public int Count => _records.Count;

    public void Flush(string dir)
        => File.WriteAllText(
            Path.Combine(dir, "assertions.json"),
            JsonSerializer.Serialize(_records,
                new JsonSerializerOptions { WriteIndented = true }));
}

public sealed record AssertionRecord(
    string Id, string Kind, string Description,
    string Expected, string Actual,
    double? Delta, double? Tolerance, string Result);
```

```csharp
// Copyright (c) Shanghai Vega Technology Co., Ltd. All rights reserved.

namespace Vega.AutoTest.Harness;

/// <summary>
/// 单次运行的落盘上下文。Runner 通过 VEGA_AUTOTEST_RUNDIR 注入；

public static class RunContext

        Directory.CreateDirectory(dir);
        return dir;
    });

    public static string Dir => LazyDir.Value;
}
```

### 3.4 Step 3 — Runner CLI

#### 命令

```bash
# 验证某工作项（默认不重编）
Vega.AutoTest.Runner verify --work-item 3478

# 强制用当前源码重编主程序后再验
Vega.AutoTest.Runner verify --work-item 3478 --rebuild

# 只跑逻辑层（秒级，不拉 GUI）
Vega.AutoTest.Runner verify --work-item 3478 --layers logic

# 环境自检
Vega.AutoTest.Runner doctor

# 列出所有可验证工作项
Vega.AutoTest.Runner list-cases --json
```

#### 参数

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--work-item <id>` | 必填 | ADO 工作项号 |
| `--case <id>` | 由 work-item 推导 | 直接指定用例 |
| `--layers logic,uia` | `logic,uia` | 跑哪些层 |
| `--rebuild` | off | 重编主程序 |
| `--configuration` | `Debug` | 构建配置 |
| `--repo-root <path>` | 自动探测 | 被测仓库根 |
| `--runs-dir <path>` | `<repo>/VegaAutoTest/runs` | 运行产物根 |
| `--timeout <sec>` | 1800 | 总超时 |
| `--json` | on | 把 result.json 路径打到 stdout 末行 |

#### 执行流水线

```
1. 解析参数 → 加载 registry → 定位用例
   ↓ 未命中 → BLOCKED/NO_CASE_REGISTERED（直接退出 2）
2. 创建 runs/<runId>/ 目录
3. doctor 前置检查：Vega.exe 是否存在、磁盘、18901 占用
4. [--rebuild] 调 run-vega-with-plugin.ps1 -NoLaunch
       成功            → rebuilt=true,  builtFromCurrentSource=true
       失败 + 有旧 exe → BUILD_FAILED_USED_STALE，继续但降级
       失败 + 无 exe   → ERROR/BUILD_FAILED_NO_FALLBACK（退出 3）
5. TargetProbe：git rev-parse / status --porcelain / exe LastWriteTime
6. 逐层 dotnet test（注入 VEGA_AUTOTEST_RUNDIR），--logger trx
7. 解析 trx + assertions.json
8. VerdictResolver 出判定
9. 写 runs/<runId>/result.json，stdout 末行打印其绝对路径
10. 按 verdict 返回退出码
```

### 3.5 L1 扫描主链：命令契约与异步任务模型（**2026-09-22 实测落地**）

需求主流程第 10–14 步（创建 Recipe → 设参 → 执行检测 → 等待完成 → 获取结果）
在插件侧补齐了可编程入口，全部经 18901：

**只读查询（GET，不受 `AllowHardwareCommands` 约束）**

| 端点 | 用途 |
| --- | --- |
| `query/run-readiness` | 一次返回「现在能不能跑扫描」+ `blockers` 数组（`tool_state_not_idle:{状态}` / `no_wafer_on_stage` / `*_unavailable` 等）；`services` 五字段暴露服务定位健康 |
| `query/scan-task?id=` | 轮询扫描任务；不带 id 返回全部任务概览 |
| `query/wafer-run?id=` | 单次 WaferRun 可断言标量集（`IsScanSuccessful` / `EffectiveDefectCount` / `counters` / 耗时），不回传缺陷明细 |
| `query/recent-wafer-runs?limit=` | 最近 WaferRun 轻量清单（投影读取，兜底定位用） |

**写命令（`POST /vega-agent/cmd/{name}`，需 `AllowHardwareCommands=true`）**

| 命令 | body | 说明 |
| --- | --- | --- |
| `recipe/create` | `{"name","folderId","open"}` | 等价 UI 新建，立即入库 |
| `wafer/load` | `{"slot","diameter","portNum"}` | 手动上片两步链已封装；已有片返回 `alreadyLoaded=true` |
| `wafer/unload` | `{}` | 手动下片 |
| `scan/start` | `{"recipeId","scanNum"}` | **异步**：立即返回 `taskId`，`query/scan-task` 轮询；单飞锁防并发 |

**异步任务模型（实测踩坑记录，两处关键时序）**：

1. **扫描路径有模态弹窗**（FS_PREOPEN 确认等），HTTP 同步等会挂死——`scan/start`
   必须异步投后台任务。L2 UIA 侧由 `DialogHandler.HandleAll` 在轮询循环里守护清理
   （混合通道分工：L1 驱动业务，L2 清弹窗）。
2. **任务终态 ≠ 结果落库**：`RunCurrentRecipeAsync` 返回（`JobRunState` 复位）时
   WaferRun 尚未入库——`SaveWaferRun` 在 DataReportingService 里是异步尾随，
   分片 + GridFS 上传（仿真 ~3.9 万缺陷）实测可拖 2–4 分钟。因此：
   - 插件：任务先置 `completed` 让轮询方尽快拿到终态；后台 watch 6 分钟补差集
     回填 `newWaferRunIds`/`waferRuns`（下次轮询可见）
   - harness `ScanFlow.GetWaferRunResult`：任务摘要为空时走
     `recent-wafer-runs`（按 RecipeName 匹配）→ `query/wafer-run` 详情的兜底链
3. **序列化大小写混用**：插件 JSON 匿名投影字段是小写驼峰，`run.XXX` 直传字段保留
   C# 属性名（如 `IsScanSuccessful`）。harness 侧统一 `ReadCaseInsensitive` 取值。

**harness 封装**：`harness/ScanFlow.cs`（RequireReadiness / WaitToolStateIdle /
CreateRecipe / LoadWafer / WaitCanRun / StartScan / PollToTerminal /
GetWaferRunResult）。正式用例 `scan-chain`（registry 已登记，
`requiresL1Api=true`），断言口径为缺陷检测模型——**Vega 无 Total Die / OK / NG**，

### 4.2 接入 Runner：异步任务模型

**注意**：不能做成同步工具调用。L2 用例 ~90s，带 `--rebuild` 要几分钟，
而 `MCPClient.CALL_TIMEOUT = 120`、`execute_cmd` 默认 30s，

新增 `tools/autotest.py`，采用 **start / poll / fetch** 三件套：

```python
"""
VegaAutoTest Runner 桥接：L0 编排层调用 L1 确定性验证。
长任务，必须异步——L2 用例 ~90s，带重编数分钟。
"""
import json, os, subprocess, threading, uuid, shlex
from pathlib import Path

RUNNER_PROJ = os.environ.get(
    "VEGA_AUTOTEST_RUNNER",
    r"D:\Code\Vega\Vega_SW.ChenLR\Vega_SW.chen.ChenLR\VegaAutoTest\runner\Vega.AutoTest.Runner")

_jobs: dict[str, dict] = {}
_lock = threading.Lock()


def _run(job_id: str, args: list[str]):
    try:
        p = subprocess.run(["dotnet", "run", "--project", RUNNER_PROJ, "--", *args],
                           capture_output=True, text=True,
                           encoding="utf-8", errors="replace", timeout=2400)
        result_path = (p.stdout or "").strip().splitlines()[-1] if p.stdout else ""
        payload = None
        if result_path and Path(result_path).is_file():
            payload = json.loads(Path(result_path).read_text(encoding="utf-8"))
        with _lock:
            _jobs[job_id].update(state="done", exit_code=p.returncode,
                                 result=payload,
                                 stderr=(p.stderr or "")[-2000:])
    except Exception as e:
        with _lock:
            _jobs[job_id].update(state="error", message=str(e))


def start_verification(work_item_id: int, rebuild: bool = False,
                       layers: str = "logic,uia") -> dict:
    args = ["verify", "--work-item", str(work_item_id), "--layers", layers]
    if rebuild:
        args.append("--rebuild")
    job_id = uuid.uuid4().hex[:8]
    with _lock:
        _jobs[job_id] = {"state": "running", "work_item_id": work_item_id}
    threading.Thread(target=_run, args=(job_id, args), daemon=True).start()
    return {"status": "success", "job_id": job_id,
            "message": f"验证已启动（工作项 #{work_item_id}）。"
                       f"请用 get_verification_status('{job_id}') 轮询，预计 2-5 分钟。"}


def get_verification_status(job_id: str) -> dict:
    with _lock:
        job = _jobs.get(job_id)
    if not job:
        return {"status": "error", "message": f"未知 job: {job_id}"}
    if job["state"] == "running":
        return {"status": "success", "state": "running", "message": "仍在执行，请稍后再查"}
    if job["state"] == "error":
        return {"status": "error", "message": job.get("message")}

    r = job.get("result")
    if not r:
        return {"status": "error",
                "message": f"Runner 退出码 {job['exit_code']} 但未产出 result.json",
                "stderr": job.get("stderr")}
    # 只回摘要，明细让模型按需取，避免吃满上下文
    return {"status": "success", "state": "done",
            "verdict": r["verdict"], "verdictCode": r["verdictCode"],
            "verdictReason": r["verdictReason"],
            "summary": r["summary"],
            "target": r["target"],
            "failedAssertions": [a for a in r["assertions"] if a["result"] == "FAIL"],
            "evidenceDir": r["evidence"]["dir"]}
```

## 8. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| UIA 用例不稳定（时序、弹窗竞态） | 假 FAIL 污染基线 | 同一用例连跑 3 次，不稳定的降级为 `BLOCKED/FLAKY`；harness 里只用显式等待，禁止 sleep |
| MongoDB 等外部依赖缺失 → 卡 busy | 大量 BLOCKED | `doctor` 前置检查依赖，缺失直接 BLOCKED 并给出修复指引，不要浪费 15 分钟跑到超时 |
| 用例覆盖率低 | 多数工作项 NO_CASE_REGISTERED | 接受现实。每修一个 Bug 顺手登记一个用例，靠时间积累；不要为了"覆盖"让模型现编用例 |
| 模型绕过 Runner 自行宣布通过 | 结论不可信 | 提示词硬约束 + 报告模板强制引用 `runId`；无 runId 的"已验证"视为无效 |
| 自动修复误改 | 主项目损坏 | 策略层 + 独立分支 + `protectedPaths` + 人工闸门 |
| Runner 与 skill 判定逻辑分叉 | 两套结论打架 | `VerdictResolver` 是唯一出处；`wi-verify` skill 改为调 Runner，不再自己判 |

### 8.1 宿主环境与控件读法（2026-09-21 实测补充）

写 #3547 / #3549 两个用例时踩到的四类问题，共同点是**都会产出看起来合理的
假结论**，比崩溃更危险——所以单列成前提，而不是当偶发问题重试：

| 风险 | 实测现象 | 对策 |
| --- | --- | --- |
| **测试进程 DPI 感知不匹配** | 150% 缩放下 UIA 返回物理坐标，但 `SendInput` 被系统再缩放一次，点击落到隔壁控件（#3549 点"Inspection"实际进了"Optics"页） | `L2TestBase` 静态构造里 `SetProcessDpiAwarenessContext(PerMonitorV2)`，强制 1:1。**这是 harness 前提，不是用例的事** |
| **负期望用正期望原语表达** | "不应弹出错误框"写成 `UiExpect.WindowAppears(...)`，超时被记成 FAIL，用例通过反而报失败 | 期望原语必须区分正/负期望：断言"不出现"要么用专门的负期望原语，要么裸调 `Dialogs.WaitForDialog` 后显式 `Assertions.Pass` |
| **WPF 模板化控件文本读法** | ComboBox 选中项走 `DisplayMemberPath`，读 `ListItem.Name` 得到 CLR 类型名而非显示文本 | 读显示值必须下钻到 `ContentPresenter` 内的 `TextBlock`；封装成 harness 方法，别让每个用例各写一遍 |
| **失败归因串层** | 用例硬断言失败被判 `HARNESS_EXCEPTION/ERROR`，报成"工具故障" | `VerdictResolver` 归因先查堆栈是否含 L2 用例帧，详见 §2.3 |

> 教训：这四条没一条是"被测程序的 Bug"，但每条都会让 verdict 说错话。
> harness 层的环境前提必须写死在基类里，用例作者不应该有机会写错。

## 9. 关键设计决策备忘

1. **进程边界而非语言统一**：不把 FlaUI 用例重写成 Python。
   UIA 在 .NET 生态最成熟，且现有 harness 已沉淀了登录流程、弹窗分类、
   `InvokePattern` 等实测踩坑结论，重写等于重踩。

2. **Runner 不引用测试工程**：只通过 `dotnet test` 子进程驱动。
   测试宿主崩溃时 Runner 仍能写出 `result.json`。

3. **BLOCKED 独立于 FAIL**：环境问题不是 Bug。混在一起会让回归基线失效。

4. **`ZERO_ASSERTIONS_MATCHED` 算 BLOCKED 不算 PASS**：
   测试绿但一条断言没命中，是最危险的假阳性。

5. **registry 显式登记而非模型推断**：宁可诚实地说"没有用例"，
   也不要让模型现编一个看起来像验证的东西。

6. **先跑失败基线再跑修复后**：没有红过的绿不可信。
